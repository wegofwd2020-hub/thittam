# Kong Single-Origin Local Proxy (#60 Phase B) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put a DB-less Kong on `http://localhost:8500` in front of the local stack, routing `/api/v1/*` to the three services that already have grpc-gateways, and make it the UI's default API origin.

**Architecture:** A `kong` service (declarative `kong.yml`, `host.docker.internal` to reach host-native Go services) is added to both local compose files; dev-start/Makefile/verify tooling is updated; the web app defaults `NEXT_PUBLIC_API_URL` to `:8500`. No Go, proto, or CI-code changes.

**Tech Stack:** Kong 3.6 (DB-less), docker-compose, bash, Make, Next.js env.

## Global Constraints

- **Kong proxy port is `8500`** — `KONG_PROXY_LISTEN: "0.0.0.0:8500"`, host mapping `"8500:8500"`, UI `NEXT_PUBLIC_API_URL=http://localhost:8500`. Not 8000, not 9000 (MinIO).
- **Host access via `extra_hosts: ["host.docker.internal:host-gateway"]`** — Kong upstreams are `http://host.docker.internal:<port>` (services run natively on the host, not in the compose network). Never `network_mode: host`.
- **DB-less:** `KONG_DATABASE: "off"`, `KONG_DECLARATIVE_CONFIG: /kong/kong.yml`, `KONG_ADMIN_LISTEN: "off"`, `kong.yml` mounted read-only.
- **`strip_path: false`** on every route (the `/api/v1/...` path must reach the gateway unchanged). Route ONLY iam/budget/project prefixes (the three with gateways); the other seven get no route (fail-fast 404).
- **No Kong CORS plugin** — the service gateways already handle CORS.
- **LOCAL DB SAFETY:** NEVER run `docker compose … -v` / `down` / `up` against `infra/local/`. Validation uses `docker compose … config` (parse only) and throwaway `docker run --rm` — never `up`/`down`. Bringing the stack up for end-to-end acceptance is the human's manual step.
- **Web changes must pass the `Web Lint & Build` gate (#179):** `cd web && npm run lint -- --max-warnings 0 && npm run build` both exit 0.
- **Commits:** Conventional Commits, scope `infra` or `api`; end every message with `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`.

- [ ] **Step 1: Write `scripts/verify-kong.sh`**

```bash
#!/usr/bin/env bash
# Verifies Kong routes the login flow end to end (#60 Phase B). Requires the
# stack up first:
#   make infra-up-full && make db-bootstrap WITH_SEED=1 && make dev-start
set -euo pipefail

KONG_URL="${KONG_URL:-http://localhost:8500}"
EMAIL="${LOGIN_EMAIL:-rajesh.kumar@xyzcba.com}"
PASSWORD="${LOGIN_PASSWORD:-demo1234}"
TENANT="${TENANT_ID:-d0000000-0000-0000-0000-000000000001}"

echo "==> POST ${KONG_URL}/api/v1/auth/login  (via Kong → iam grpc-gateway)"
# -f: fail (non-zero) on any non-2xx — e.g. a missing Kong route returns 404.
resp=$(curl -sf -X POST "${KONG_URL}/api/v1/auth/login" \
  -H 'Content-Type: application/json' \
  -H "X-Tenant-ID: ${TENANT}" \
  -d "{\"email\":\"${EMAIL}\",\"password\":\"${PASSWORD}\"}")

if echo "${resp}" | grep -q '"access_token"'; then
  echo "OK: Kong routed login to iam; access_token present in the TokenPair."
else
  echo "FAIL: login succeeded (2xx) but no access_token in response:"
  echo "${resp}"
  exit 1
fi
```
Then make it executable:
```bash
chmod +x scripts/verify-kong.sh
```
(The login response is a flat snake_case `TokenPair` with `access_token` — `proto/thittam/iam/v1/iam.proto:161-167`. Tenant resolves from the seeded demo tenant; the `X-Tenant-ID` header matches the other quick-login examples.)
